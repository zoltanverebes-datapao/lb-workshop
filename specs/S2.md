# S2: Database connection and migration infrastructure

Inherits: `docs/conventions.md`, `docs/rubric-base.md`, `docs/glossary.md`

## Goal

Give the application a working PostgreSQL connection and a Yoyo migration
pipeline so that subsequent items can create tables and evolve the schema.
After this item, the app connects to a local Postgres instance configured via
environment variable, migrations can be applied via SQL scripts, and the
necessary driver dependencies are present in `pyproject.toml`.

No ORM is used. Database access is via `psycopg` 3 async connection pool
with raw SQL throughout.

## Scope
In:
- `backend/pyproject.toml` -- add database dependencies
- `backend/app/db.py` -- async connection pool, `get_conn` dependency
- `backend/migrations/` -- Yoyo migration scripts directory (empty initially)
- `backend/app/main.py` -- lifespan hook that runs Yoyo migrations on startup
- `backend/tests/conftest.py` -- database-aware test fixtures with setup/teardown
- `backend/tests/test_db.py` -- connection smoke test
- `backend/scripts/init_db.py` -- database initialization script for local dev
- `backend/scripts/truncate_db.py` -- database truncation script for test cleanup
- `docker-compose.yml` -- Docker Compose configuration for local Postgres
- `scripts/start_postgres.sh` -- Startup script that checks and starts container only if needed

Out:
- Databricks Lakebase connection or dialect (owner: future item)
- Domain tables and their migrations (owner: per-entity items)
- `/__test__/*` seed routes (owner: first item that declares fixtures)
- Frontend changes (no frontend touched)
- Any ORM (no SQLAlchemy, no models directory)

## Interface contract

### Environment variables

| Variable       | Required | Example                                              | Purpose                     |
|----------------|----------|------------------------------------------------------|-----------------------------|
| `DATABASE_URL` | yes      | `postgresql://postgres:postgres@localhost:5432/app`   | psycopg 3 connection string |

The application must refuse to start (raise on import or lifespan) if
`DATABASE_URL` is not set.

### Module: `backend/app/db.py`

Exports:

| Name                | Type                              | Purpose                                  |
|---------------------|-----------------------------------|------------------------------------------|
| `pool`              | `psycopg_pool.AsyncConnectionPool`| Async connection pool created from `DATABASE_URL` |
| `get_conn`          | async generator                   | FastAPI `Depends` yielding an `AsyncConnection`   |

### Migration layout (Yoyo)

```
backend/
  migrations/              # Yoyo migrations directory
    001_init.sql           # numbered scripts, run in order
    002_create_products.sql
```

Yoyo automatically discovers and applies migrations in order. Each migration is
tracked in a `_yoyo_migration` table in the database.

Migration files can be:
- **SQL scripts** (`.sql`): raw PostgreSQL dialect SQL
- **Python scripts** (`.py`): must define `steps` as a list of
  `step(apply=..., rollback=...)` tuples

Example SQL migration:
```sql
-- 001_init.sql
CREATE TABLE example (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

Example Python migration:
```python
# 001_init.py
from yoyo import step

steps = [
    step(
        "CREATE TABLE example (id UUID PRIMARY KEY, name TEXT)",
        "DROP TABLE example"
    )
]
```

### Migration on startup

The FastAPI lifespan (async context manager on `app`) runs migrations via Yoyo
before yielding. This is idempotent -- running it when all migrations are already
applied is a no-op.

### Dependencies added to `pyproject.toml`

| Package           | Purpose                          |
|-------------------|----------------------------------|
| psycopg[binary]   | async PostgreSQL driver (v3)     |
| psycopg-pool      | async connection pool            |
| yoyo-migrations   | schema migrations                |

These are added to the existing `[project.dependencies]` list.
No SQLAlchemy or ORM packages.

### Test infrastructure

`backend/tests/conftest.py` must:

1. Read `DATABASE_URL` (falling back to a sensible localhost default for CI).
2. Provide an async fixture that yields a psycopg `AsyncConnection`.
3. Run database initialization (apply all Yoyo migrations) before tests.
4. Run database truncation (clear all data but keep schema) after each test or session.

`backend/tests/test_db.py` contains at least one test that opens a connection and
executes `SELECT 1`.

### Database setup/teardown scripts

Two standalone scripts are provided for manual and test use:

**`backend/scripts/init_db.py`** — Initialize the database schema:
- Reads `DATABASE_URL` from environment (or uses localhost default)
- Applies all pending Yoyo migrations
- Creates the `_yoyo_migration` tracking table if it doesn't exist
- Can be called multiple times (idempotent)

**`backend/scripts/truncate_db.py`** — Clear all data (for test isolation):
- Reads `DATABASE_URL` from environment
- Truncates all user-created tables (preserves schema and `_yoyo_migration`)
- Can be called between test runs to reset state
- Does NOT drop the `_yoyo_migration` table

These scripts are used by `conftest.py` fixtures and can be run manually for development.

### Docker setup

**`docker-compose.yml`** — Defines the local Postgres service:
- Image: `postgres:16`
- Environment: `POSTGRES_PASSWORD=postgres`
- Port mapping: `5432:5432`
- Volume: optional, for persistence (e.g., `postgres_data:/var/lib/postgresql/data`)
- Service name: `postgres`

**`scripts/start_postgres.sh`** — Convenience script for local development:
- Checks if a container named `lakebase-postgres` is already running
- If running, outputs status and exits 0 (idempotent)
- If not running, starts it via `docker-compose up -d`
- Waits for the database to be ready (polls TCP connection on localhost:5432)
- Creates the test database `test_s2` if it doesn't exist
- Suitable for development workflows (not required for CI; Playwright handles containers)

Example usage: `bash scripts/start_postgres.sh`

## Notes

- The `docker-compose.yml` uses a service name `postgres` and container name
  `lakebase-postgres`. The `start_postgres.sh` script uses the container name to
  check if it's already running.

- `start_postgres.sh` should:
  - Check if `lakebase-postgres` container exists and is running
  - If yes, print status and exit 0
  - If no, run `docker-compose up -d` to start it
  - Wait up to 30 seconds for port 5432 to be ready (TCP poll)
  - Create database `test_s2` via `psql` if it doesn't exist

- The script is optional for CI environments (Playwright container setup handles it),
  but essential for local development workflows.

- `psycopg` (v3) is the async-capable driver. Do NOT use `psycopg2` or
  `asyncpg`. The connection URL scheme is `postgresql://` (plain psycopg format).

- **Yoyo** automatically discovers migrations in the `migrations/` directory and
  tracks applied migrations in a `_yoyo_migration` table. Migrations are numbered
  and applied in order (e.g., `001_init.sql`, `002_add_products.sql`).

- The lifespan migration-on-startup (via `init_db.py` logic) is a convenience for
  development. In production, migrations would be run as a separate step. But for
  this project the lifespan approach is acceptable.

- `init_db.py` and `truncate_db.py` are standalone scripts that can be called
  from `conftest.py` fixtures or manually. They should handle the case where the
  database does not yet exist (by connecting to the default `postgres` database
  and creating the target database).

- Databricks Lakebase uses a PostgreSQL-compatible interface, so the same
  `psycopg` driver and `DATABASE_URL` pattern will work when that
  environment is configured. No code changes are expected for Lakebase
  compatibility; only the `DATABASE_URL` value changes. This is explicitly out
  of scope for implementation and testing in this item.

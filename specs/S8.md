Status: **IMPLEMENTED**

Depends on: S3 (products/stock_levels tables, ProductRepository), S4 (frontend

## Goal

A person opening the app sees a table of products, ten per page, showing each
product's id, name, and current stock level, with Previous/Next buttons that
walk the whole catalogue. The API behind it pages by keyset cursor, so page 500
costs the same as page 1 and no request ever counts the table. This is the first
API route that returns domain data and the first real page in the frontend.

## Interface contract

### Route

```
GET /api/products?limit=<int>&cursor=<opaque>
    200 -> { products: ProductListItem[], nextCursor: string | null }
    422 -> { error: string, field: "limit" | "cursor" }
```

`ProductListItem`:

```
{
  id: string,                 // UUID
  name: string,
  stockLevel: { quantity: number, measure: Measure } | null
}
```

`Measure` is the closed set in the glossary: `pieces` | `kilogram` | `gram` |
`litre`.

The item has **exactly** these three keys. `description`, `createdAt`, and
`updatedAt` are not returned by this route.

### `stockLevel` -- the aggregation rule

A product may have zero, one, or many `stock_levels` rows. `stockLevel` is the
single row with the greatest `created_at`, ties broken by the greatest `id`.
Quantities are **never** summed: `3 kilogram` and `5 pieces` are not `8` of
anything. A product with no `stock_levels` row gets `stockLevel: null`.

### Ordering

`ORDER BY created_at ASC, id ASC` -- the same direction `ProductRepository.list_all`
already uses, extended with `id` so the order is total. `created_at` alone is not
unique: rows inserted in one transaction share `now()`.

### Pagination -- keyset, not offset

The cursor is the `(created_at, id)` of the last row of the page just returned.
The next page is `WHERE (created_at, id) > (cursor_created_at, cursor_id)`, which
the composite index serves directly. `OFFSET` is not used anywhere, and no
request issues `COUNT(*)`.

`nextCursor` is determined by selecting `limit + 1` rows and discarding the
extra: if `limit + 1` rows come back there is a next page, otherwise
`nextCursor` is `null`. There is no second query.

Cursor encoding (specified so the builder does not invent a format, **not** so
tests can construct one -- tests must treat cursors as opaque and only reuse
values returned in `nextCursor`):

```
base64url-no-padding( "<created_at ISO-8601 with Z>|<id>" )
```

### Query parameters

| Param | Type | Default | Rules |
|---|---|---|---|
| `limit` | integer | `10` | `1 <= limit <= 100`. Anything else -> 422, `field: "limit"` |
| `cursor` | string | absent | Must decode to the format above. Undecodable -> 422, `field: "cursor"` |

- `cursor` absent **or** empty string (`?cursor=`) -> first page, 200.
- A well-formed cursor that points past the last row -> `200 { products: [], nextCursor: null }`. Not 404.
- Any other query parameter (`sort`, `order`, `offset`, `q`, `page`, ...) is
  **ignored**: same status, same body as if it had not been sent. No 422.

### Validation error body

FastAPI's default 422 body does not match the house shape. Register a
`RequestValidationError` handler that emits `{"error": <message>, "field": <name>}`
for the first failure only, where `<name>` is the query parameter name exactly
as spelled in the URL (`"limit"`, `"cursor"`), never `"query.limit"` or
`["query", "limit"]`.

### Test fixtures

Mounted only when `APP_ENV=test`, declared with `include_in_schema=False` so
they never reach the OpenAPI document. Each seed route first empties
`stock_levels` then `products`, so fixtures are independent of one another.

```
POST /__test__/seed/products/empty          200 -> { fixture, productIds: [] }
POST /__test__/seed/products/three          200 -> { fixture, productIds: [...] }
POST /__test__/seed/products/twenty-five    200 -> { fixture, productIds: [...] }
POST /__test__/seed/products/ties           200 -> { fixture, productIds: [...] }
POST /__test__/seed/products/<anything-else> 404
```

`productIds` is in the exact order `GET /api/products` will return the products,
so tests never have to re-derive the ordering.

- **`products/empty`** -- both tables emptied, nothing inserted.

- **`products/three`** -- `Alpha`, `Bravo`, `Charlie` with `created_at`
  `2026-01-01T00:00:00Z`, `+00:01`, `+00:02`. Stock levels: Alpha one row
  `(5, pieces)`; Bravo none; Charlie one row `(12, kilogram)`.

- **`products/twenty-five`** -- `Product 01` .. `Product 25`, `created_at`
  `2026-01-01T00:00:00Z` plus N minutes for `Product NN`. Stock levels:
  - `Product 01` .. `Product 23`: exactly one row, `quantity = NN * 10`,
    `measure` cycling `pieces, kilogram, gram, litre` starting at `Product 01`
    = `pieces`.
  - `Product 24`: **no** `stock_levels` row.
  - `Product 25`: **two** rows -- `(7, gram)` at `2026-03-01T00:00:00Z` and
    `(3, litre)` at `2026-03-02T00:00:00Z`. The API must report
    `{"quantity": 3, "measure": "litre"}`.

- **`products/ties`** -- 5 products sharing one identical `created_at`
  (`2026-02-01T00:00:00Z`), with fixed ids
  `00000000-0000-4000-8000-00000000000{1,2,3,4,5}` named `Tie A` .. `Tie E` in
  that id order. Each has one row `(1, pieces)`. This fixture exists to catch a
  `WHERE created_at > cursor` implementation that drops or repeats rows.

### Environment guard

- `/__test__/*` is mounted only when `APP_ENV == "test"`; with `APP_ENV` unset
  those paths return 404.
- With `APP_ENV == "test"` and a `DATABASE_URL` whose host is neither
  `localhost` nor `127.0.0.1`, the app raises at startup rather than serving.

### Frontend

Page size is a constant `PAGE_SIZE = 10` exported from
`frontend/src/api/products.ts`, sent explicitly as `?limit=10`.

Rendered structure (`/app`):
- The existing `data-testid="app-root"` wrapper and `<h1>Lakebase</h1>` stay.
- Below it, `<h2>Products</h2>`.
- The table element carries `aria-label="Products"`.
- Column headers, in order: `ID`, `Name`, `Stock level`.
- Stock cell text: `"{quantity} {measure}"`, e.g. `120 kilogram`. When
  `stockLevel` is `null`, the em dash `—` (U+2014).

States, mutually exclusive:

| State | Rendered | Absent |
|---|---|---|
| loading (before first response) | `product-loading` | table, empty, error |
| success, >= 1 row | `product-table`, `product-row` x N, `product-prev-page`, `product-next-page` | `product-empty`, `product-loading` |
| success, 0 rows on first page | `product-empty`, text `No products` | `product-table`, both page buttons |
| request failed (non-2xx or network) | `product-error`, text starting `Failed to load products` | `product-table` |

Buttons:
- `product-prev-page` -- disabled on the first page.
- `product-next-page` -- disabled when `nextCursor` is `null`.
- "Previous" is a client-side stack of cursors already visited. The API is
  never asked to page backwards.

Test IDs: `product-table`, `product-row`, `product-id-cell`, `product-name-cell`,
`product-stock-cell`, `product-next-page`, `product-prev-page`, `product-empty`,
`product-error`, `product-loading`.

Accessible names: table `Products`; buttons `Next page` and `Previous page`
(visible button text); heading `Products`.

TanStack Table is the table and pagination engine, not decoration:
`ProductTable.tsx` uses `useReactTable`, `getCoreRowModel`, `flexRender`, and
`manualPagination: true`. Rows and cells are rendered through the table
instance's `getRowModel()` / `flexRender`, not by mapping the raw response array
into `<td>`s.

The frontend never contains an absolute API host. Requests go to the relative
path `/api/products`; `vite.config.ts` proxies `/api` to `http://localhost:8000`
for `npm run dev` only.

Contract tests live in `tests/contract/S8.spec.ts` and drive the UI at
`http://localhost:8100/app` (the backend serves the built bundle, per S5). Each
test is named `C<n>: ...` so `-g "C<n>"` selects it.

## Notes

- **Why keyset and not `OFFSET`.** `products.id` is a random UUID, so there is
  no monotonic integer to page on, but that does not force offset paging --
  it only forces the sort key to be a compound one. `OFFSET n` makes Postgres
  walk and discard `n` rows on every request, so cost grows linearly with page
  number, and a row inserted between two requests shifts every later page,
  silently duplicating or skipping items. `(created_at, id)` is unique and
  totally ordered, so `WHERE (created_at, id) > (?, ?) ORDER BY created_at, id
  LIMIT n` is an index range scan of constant cost and is stable under
  concurrent inserts. The `id` component exists purely to break `created_at`
  ties -- `now()` is per-transaction, so a bulk insert produces many rows with
  an identical timestamp. Fixture `products/ties` is the regression test for
  exactly that.

- Row-values (`(a, b) > (%s, %s)`) are the clean way to write the predicate in
  Postgres and use the composite index directly. `a > %s OR (a = %s AND b > %s)`
  is equivalent but easier to get wrong.

- Suggested shape of the query, not prescriptive beyond the criteria:

  ```sql
  SELECT p.id, p.name, p.created_at, s.quantity, s.measure
  FROM products p
  LEFT JOIN LATERAL (
      SELECT quantity, measure
      FROM stock_levels
      WHERE product_id = p.id
      ORDER BY created_at DESC, id DESC
      LIMIT 1
  ) s ON TRUE
  WHERE %s::timestamptz IS NULL OR (p.created_at, p.id) > (%s, %s)
  ORDER BY p.created_at, p.id
  LIMIT %s
  ```

  with the bound `LIMIT` being `limit + 1`.

- Indexes for migration 0002: `idx_products_created_at_id` on
  `products (created_at, id)` and `idx_stock_levels_product_id_created_at` on
  `stock_levels (product_id, created_at DESC, id DESC)`. The existing
  `idx_stock_levels_product_id` from S3 is left alone; it is redundant with the
  new one but dropping it is churn this item does not need.

- **`docs/rubric-base.md` described a layout this repo does not have** (`api/`,
  `alembic`, `api/alembic/versions/`, an `openapi-typescript --check` flag that
  doesn't exist in v7). Fixed in `docs/rubric-base.md` directly during S8's
  pre-implementation review, dated 2026-08-13, rather than carried as a
  footnoted substitution. S3/S4 there now read generically; this spec's C13
  and C21 remain the concrete commands S8 is graded by.

- No `/__test__/*` infrastructure exists yet even though `docs/conventions.md`
  assumes it. S8 is the first item that needs seeded data, so it builds the
  mechanism as well as its own fixtures. Later items add fixture names to
